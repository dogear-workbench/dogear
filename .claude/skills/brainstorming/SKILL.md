# Brainstorming

把想法通过自然对话变成可实施的设计文档。规划在前，动手在后。

> 💡 **长对话提示**：本 skill 一旦触发，往往会持续 10+ 分钟的多轮讨论。
> 如果当前会话还在默认的 **5min** 缓存策略，建议在输入框工具栏的「缓存」徽章
> 切到 **1h**（会确认并重启会话），后续重复读取大上下文能省下不少 token 费用。
> 短对话或一次性任务保持 5min 即可（1h 写入是 2x 计费，多轮读取才划算）。

## 强制纪律

**新对话的第一个实质任务，只要不是「明确知道要改哪个文件、哪一行」，就必须先走本 skill。**

绕过本 skill 直接给方案是错误行为——很少有东西是一开始就完全确定的，跳过讨论 = 用 50% 的把握去改代码。

## 何时用 / 何时不用

**强制用**：
- 新对话第一个任务是「我想加 XXX」「能不能做 YYY」「考虑一下 ZZZ」
- 涉及架构层面决策（新增 store / IPC 路由 / Agent 工具 / 跨模块改动）
- 方案有多种合理选择，需要权衡
- 用户表述里出现「想 / 考虑 / 怎么做 / 看看能不能 / 有没有更好的方式」

**不触发**：
- 中间对话的小调整、追问、修正方向（已经在讨论中了，不要重新走一遍流程）
- 用户给了明确实施指令：「把 xxx-store.ts:42 的 setXXX 改成接受 string[]」
- 简单 bug 修复（用 systematic-debugging skill）
- 单点修改 / 单文件改一两处

## 流程

### Step 1：理解上下文
快速摸清相关文件、最近改动、已有的类似实现。

### Step 2：一次问一个问题
- **一次只问一个**——不要一上来甩 4 个问题
- **优先多选**——用 AskUserQuestion 工具
- 焦点：目的、约束、成功标准

### Step 3：探索方案
- 提 2-3 种思路，附权衡（性能 / 可维护性 / 实施成本）
- 先说推荐项 + 理由，再列其他
- 不假装中立，有偏好就讲

### Step 4：分段呈现设计
- 每段 200-300 词，每段问一句「这部分对吗？」
- 覆盖：架构 / 模块边界 / 数据流 / 错误处理
- 不强制写测试章节（项目偏好不写单测）

## 设计文档落盘

讨论清楚后，写到 `docs/plans/YYYY-MM/YYYY-MM-DD/<topic>-design.md`：

```markdown
# <Topic> 设计

**背景**：（为什么要做这个）
**目标**：（要达成什么）
**架构**：（核心做法 + 排除的选项及原因）
**模块边界**：（涉及哪些文件 / store / service / IPC 路由）
**数据流**：（从 X 到 Y 怎么走）
**错误处理 / 边界情况**：（已识别的）
**未决问题**：（讨论时没拍板的，留给实施时补）
```

## 后续衔接

设计文档落盘后问用户：「要按这个设计写实施计划吗？」
- 是 → 用 staged-impl skill
- 否 → 结束，设计文档留作未来参考

## 关键原则

- 一次一个问题，不堆问题
- YAGNI，砍掉没必要的特性
- 多选优先（AskUserQuestion）
- 先推荐再列选项，不假装中立
- 分段验证，别一次甩完整设计
- 拿不准就回头，不要硬撑

# Stock Picking

把用户的模糊选股需求拆成"定条件 → 预热+评分 → 子会话深挖出报告"三步 SOP。全流程数据源分级兜底，缺数据必须留白。

## 新范式：预热 + 评分（v2 重构后）

传统流程是"agent 手工串行调 N 次财报 + N 次信号 + N 次公告"——问题是候选池截断偏差大、执行错误多、重跑成本高（换权重就要全部重来）。

v2 收敛到两个工具：

- **一次 `PreheatCandidatePool`** 完成所有原始数据拉取，全部落地本地缓存（财报按 reportPeriod 永久缓存 / 公告列表当天缓存 / K 线 JSONL 增量缓存）
- **一次 `RankCandidates`** 按权重公式打分排序（**纯本地算，秒级**）
- 用户可以反复调 `RankCandidates` 换权重看不同视角，**不用重复预热**

工具在 `dogear-stock-picking` MCP server 下。**用户需要在设置页「工具包」里勾上「候选池预热」才能调用**——本 skill 触发时如果检测到 agent 没有这两个工具，先明确告诉用户"请去设置页开启候选池预热工具包再重试"，不要退回旧的手工串行姿势。

## 铁律（违反 = 报告作废）

1. **缺数据必须明确留白**——某段没拿到数据就直说"未获取"或空着，禁止用"该公司盈利能力尚可 / 基本面稳健"这类敷衍话填补。宁可段落是空的，不要看起来像模像样但内容是编的。
2. **`PreheatCandidatePool` 返回 `status.total = 0` 时直接告诉用户"当前条件无候选，是否放宽条件"，不能凭空造股票**——预热结果的 status 段是唯一真源，透传给用户看。

## 3 步 SOP

### Step 1：定条件（对话追问，不调工具）

问用户 3 组条件，明确告知"软条件的 ROE/增速门槛不做硬筛，会通过评分权重体现"：

- **硬条件（必问）**：
  - 行业/板块（**证监会 CSRC 分类名**，如 `C39计算机、通信和其他电子设备制造业`）——**不确定名字时先调 `ListIndustries` 关键词过滤查真实值域**（用户说"科技"实际可能对应多个 CSRC 分类，需要逐一列出让用户选，或者多传几个到 `PreheatCandidatePool` 的 `industries` 数组一次预热多个板块）
  - 市值区间（如"100-500 亿"）——注意 baostock 主源目前无股本数据，`market_cap_min/max` 多数情况下不生效，参数照传即可但期望值不要过高
  - PE 上限（如"< 30"，一般也默认排除亏损股）
  - 是否排除 ST（默认排除）
- **软条件（选问）——不做硬筛，交给 RankCandidates 权重体现**：
  - ROE 偏好 → 加大 `roe` 权重
  - 净利润增速偏好 → 加大 `growth` 权重
  - 估值敏感 → 加大 `valuation` 权重
- **产出数量**：默认 3-5 只，最多 10 只（这个数字是最终深挖的 N，与预热 pool 的 limit=50 不是一回事）

追问模板参考：
> 帮你圈候选前先对齐几个条件：
> 1. 想在哪个板块/行业？（不确定我先查东财板块名对应的 CSRC 分类）
> 2. 市值范围大概多少？PE 上限？要不要排除亏损股和 ST？
> 3. 更看重估值、成长性还是技术信号？（默认权重是 ROE 25% / 增速 25% / 估值 20% / 信号 15% / 催化剂 10% / 惩罚 5%）
> 4. 最终想深挖几只？（默认 3-5 只）

**不要跳过 Step 1 直接跑工具**——用户没说清条件时预热出的候选池可能整个方向就错了。

### Step 2：预热 + 评分（一次预热 + 秒级重排序）

新架构下这一步只有两个工具调用：

1. **`PreheatCandidatePool`** — 传硬条件（`industries` / `price_max` / `pe_max` / `market_cap_min` / `exclude_negative_pe` / `exclude_st` / `limit=50`），一次拿到完整候选池数据（含 ROE / 净利同比 / 技术信号 / 公告标题）。首次约 40s，同天重跑 <15s（财报缓存命中 + 公告当天缓存命中）。
   - **工具返回的 markdown 表末尾有一个 ```json 代码块**，内容是 `{ "candidates": [...] }`。这个 JSON 数据要**原样保留在对话上下文里**，下一步 RankCandidates 会用到（agent 不需要显式复制，直接引用即可）。
   - 若 `status.total = 0`：按铁律 2 处理，停下问用户是否放宽条件。
   - 若 `status.failuresByCategory` 里 `announcements` 或 `signals` 失败率 > 30%：给用户提示"本轮公告/信号数据部分缺失（原因见预热结果的数据缺口段），可能影响评分准确性"，但**继续流程**（预热部分数据仍有价值）。

2. **`RankCandidates`** — 把上一步的 `candidates` 数组 + weights（可选）传进来，返回按综合分排序的 Top 15。
   - 参数 `candidates`：从预热结果的 JSON 块里取 `.candidates`
   - 参数 `weights`：如果 Step 1 用户说了偏好（"更看重估值"）就调整，否则不传（用默认权重）
   - 参数 `top`：默认 15，够用
   - 输出是 markdown 表，列：`| 排名 | 代码 | 名称 | 综合分 | ROE分 | 增速分 | 估值分 | 信号分 | 催化剂分 | 惩罚 |`
   - 表格上方一行标注实际生效的权重百分比（若有维度因全池缺失被归零，会额外一行说明"XX 维度全池缺失，权重已重分配"——这是**真实情况**，透传给用户不用解释太多）

**产出【综合评分简表】**（RankCandidates 输出的 markdown 表），然后停下问用户：
> 以上 15 只按当前权重排序。你想深挖哪 3-5 只？（也可以先换权重再看一版，比如"把估值加到 40%"，我会秒级重排）

**关于换权重**：用户如果说"再看一版更看重技术信号"，只需要**再调一次 RankCandidates**（同一份 candidates 数据 + 新 weights），不要重新预热。这就是新架构的核心价值。

### Step 3：子会话并行深挖（每只 1 个子会话）

对用户挑中的 N 只（3-5 只），主会话用 `CreateSessionBatch` **一次派 N 个子会话**并行深挖。

**主会话职责**：
- 用 `CreateSessionBatch` 一次派 N 个子会话，每个 `outputPath` 用 `reports/<code>.md`
- 每个子会话 task 描述明确带上：该股票的代码/名称、Step 2 简表里的关键数据（RankCandidates 已经给出的综合分/各维度分/信号数/公告数）、要求输出的报告结构（见下方模板）、交付路径
- `WaitForMessage(fromSessionIds=[...])` 等所有子会话交付
- 读所有子会话产出的报告（用 `ReadGroupFile`），组装成最终交付：
  - 横向对比章节（技术面/基本面/催化剂三维度并排）
  - 【数据缺口】汇总表
  - 【最终推荐】1-2 只 + 理由（结合综合分和深挖后的判断）

**子会话职责**（每只独立执行，内部串行）：

1. **技术面**（本地缓存加持，无 API 压力）：
   - `GetKLineData(period='daily', limit=120)` + `CalcIndicators(indicators=['MACD','KDJ','RSI','BOLL','MA'])` → 日 K 状态
   - `GetKLineData(period='weekly', limit=52)` + `CalcIndicators(indicators=['MACD'], period='weekly')` → **周 K MACD 长周期趋势**
   - `CalcIndicators(indicators=['MA'], params={MA:{N:[60,120]}})` → **中长期均线方向（MA60/MA120 上/下/横）**
   - **年内价格位置** = (当前价 - 近 250 日 min) / (近 250 日 max - 近 250 日 min)，用返回的 K 线数据自己算（写死一个内联公式，不用调工具）

2. **基本面**（Step 1 缓存加持，秒回）：
   - `GetFinancials(periods=4)` → 拉最近 4 期财报（缓存命中不走 Python）
   - `CompareIndustry` → 行业内相对估值

3. **催化剂**（Step 2 缓存加持）：
   - `ListAnnouncements(since='近 30 天', limit=10)` → 拿标题列表（当天缓存命中）
   - 从中挑最重要 1-2 条调 `ReadAnnouncement` 读全文（PDF 首次拉后落 hash 缓存）

4. **组装报告**写到 `shared/reports/<code>.md`（`WriteGroupFile`），格式见下方模板

**为什么可以并行**：数据源全部有本地缓存（Step 1-4 改造后），子会话读缓存不撞任何上游 API。唯一并发瓶颈是 `ReadAnnouncement` 首次拉 PDF（走巨潮限流），但 5 个并发在 limiter 下完全 OK，不需要额外调度。

**报告结构模板**（每只子会话产出）：

```markdown
### <代码> <名称>

**推 / 观望 / 不推**（三选一 + 一句话理由，结合评分表综合分和深挖发现）

#### 技术面
- 日 K：MACD/KDJ/RSI/BOLL 现状 + 均线排列（有信号写具体日期）
- 周 K：MACD 长周期趋势（金叉/死叉/横盘）
- 中长期均线：MA60/MA120 方向
- 年内价格位置：XX%（0=年内最低 / 100=年内最高）

#### 基本面
PE / PB / ROE / 净利润增速 / 行业对比；缺哪项就留白，别编

#### 催化剂
最近公告要点（1-2 条，含发布日期）；无近期公告写"近 30 天无重要公告"

#### 综合评分背景
（引用 Step 2 RankCandidates 结果里该股的综合分和各维度分，说明为什么排在这个位置）

---
```

**报告结尾必列【数据缺口】表**（哪只哪个维度没拿到 + 原因）：

```markdown
## 数据缺口

| 股票 | 缺失维度 | 原因 |
|---|---|---|
| 600XXX | 财报 ROE | GetFinancials 接口失败 |
| 002XXX | 最新公告 | ListAnnouncements 空返回 |
```

无缺口时写"无"，不省略这段。

## 综合评分权重

`RankCandidates` 默认权重：

| 维度 | 权重 | 数据来源 |
|---|---|---|
| ROE | 25% | 最近年报 ROE 分位数 |
| 净利增速 | 25% | `max(年报, 一季报)` 净利同比分位数 |
| 估值 | 20% | PE 倒数分位数（越低越好） |
| 技术信号 | 15% | 近 7 天信号加权总分（时间衰减 1.0→0.3） |
| 公告催化剂 | 10% | 近 30 天公告关键词加权总分 |
| 业绩下滑惩罚 | -5% | 净利同比 < -20%（年报）或 < -30%（季报）触发满惩罚 |

**关于分位数**：每个维度在候选池内部排序打 0-100 分，不是全市场绝对分。所以同一只股票在不同候选池里综合分可能不同——这是设计如此，选出的是"在这个池子里最优的一批"。

**用户想调权重**：直接告诉 agent"更看重估值"或"技术面权重加到 30%"，agent 传 `weights` 参数给 RankCandidates 即可。权重不需要和为 1，工具内部会自动归一化。

**关于维度归零**：某维度候选池内全部缺失（比如所有候选的 `netProfitYoYQuarter` 都是 null——当前 baostock 主源就是这情况），该维度权重会自动归零，其他维度按比例放大。工具输出会明确告知"XX 维度全池缺失，权重已重分配"。

## 子会话并行边界（v2）

缓存架构改造后，所有数据源在预热完成后都是本地读，子会话并行不撞任何 API：

| 数据源 | 预热前 | 预热后（本 skill 场景） |
|---|---|---|
| baostock 全 A 快照 | ✅ 已缓存 | ✅ 本地读 |
| 同花顺财报 | ❌ 0.5s 单股限流 | ✅ Step 1 缓存命中（按 reportPeriod 永久 key） |
| 东财 K 线 | ⚠️ 令牌桶 | ✅ JSONL 增量命中 |
| 巨潮公告标题列表 | ⚠️ 令牌桶 | ✅ Step 2 当天 key 缓存 |
| 巨潮 PDF 全文 | ⚠️ 令牌桶 | ✅ hash 缓存（首次深挖时首次拉，之后永久命中） |

**唯一并发瓶颈**：子会话如果每只都要 `ReadAnnouncement` 拉从未缓存过的 PDF，会走巨潮 limiter 排队。5 只子会话的量级完全 OK；超过 10 只就要评估是否分批。

## 数据源分级兜底表

| 层级 | 场景 | 处理姿势 |
|---|---|---|
| 一级：预热本身 | `PreheatCandidatePool` 抛异常 / 返回 `isError: true` | **直接中止 SOP**，告诉用户底层数据源不可用（通常是 baostock 或 Python bridge），稍后重试 |
| 一级：预热本身 | `status.total = 0` | 按铁律 2 处理，问用户是否放宽条件 |
| 二级：预热维度缺失 | `status.failuresByCategory` 部分维度失败率 < 30% | 继续流程，RankCandidates 会自动处理（缺失的股票该维度 0 分或该维度权重归零） |
| 二级：预热维度缺失 | `announcements` / `signals` 失败率 > 30% | 给用户提示"XX 维度数据缺失较多可能影响评分"，但继续流程 |
| 三级：深挖细节 | 子会话内单只单维度失败（K线/信号/公告/行业对比任一） | 该维度写"未获取"，其他维度继续；子会话报告结尾【数据缺口】表登记；主会话汇总时保留 |
| 三级：深挖细节 | 子会话整个失败（超时 / 拒绝交付） | 该只在最终报告里标"深挖失败：<原因>"，其他子会话继续，不影响整体 |

## 边界与限制

- **候选池 limit 上限 100**：`PreheatCandidatePool` 的 `limit` 参数最大 100，默认 50。过大会拖慢预热（每 +10 只约 +5s）。用户没特殊要求时用默认。
- **用户不指定行业时**：**必须追问**，不默认全市场跑（`industries` 参数是 min(1)，不允许空数组）。
- **`market_cap_min/max` 目前不生效**：baostock 主源无股本数据，参数照传但期望值不要过高。用户强调市值时告知这一限制，建议改用 PE 或行业过滤代替。
- **`netProfitYoYQuarter` 目前恒为 null**（baostock 主源限制），实际 growth 维度只用年报口径。等主数据源覆盖季报后自动生效，本 skill 不用改。
- **观察 / 跟踪 SOP 暂未实现**：如果用户在 Step 3 后问"接下来每天怎么跟踪"，回答"跟踪工作流暂未实现，你可以把深挖过的股票加到自选股手动跟踪"。
- **单次全流程预算**：预热 ~40s（首次）/ <15s（同天重跑）+ 评分 <1s + 5 个子会话并行深挖 ~60s（有 PDF 首次拉时）。整体 2-3 分钟。

# Systematic Debugging

随机试错浪费时间，且制造新 bug。"先打个补丁"会掩盖真正问题。

## 铁律

**没有根因调查就不允许提修复方案。**

如果还没完成 Phase 1，就不能提任何 fix。对应全局 CLAUDE.md「根因优先」原则。

## 何时用 / 何时不用

**强制用**：
- 任何报错、异常、bug
- 构建失败、lint 失败
- 行为不符合预期（"为什么这里没刷新"）
- 性能问题、卡顿、内存问题
- 集成问题（IPC 通信、Worker 通信）

**特别要求用**（这些场景反而最容易走捷径）：
- 时间紧，越紧越要克制
- "一行就能修好"看起来很明显
- 已经试过几个 fix 都不行
- 自己其实没完全理解问题

**不绕过**：
- 问题看起来简单（简单 bug 也有根因）
- 赶时间（系统化反而比瞎试快）

## 四个阶段（必须按序）

### Phase 1：根因调查

任何修复前必须先做：

1. **认真读错误信息**——完整读 stack trace、行号、错误码，错误信息常常就含答案
2. **稳定复现**——能稳定触发吗？步骤是什么？不能复现 → 收集更多数据，不要猜
3. **检查最近改动**——`git diff` / `git log`，新装依赖、配置变更
4. **多组件系统追根**——dogear 有 Renderer ↔ tipc ↔ Main ↔ Worker ↔ SDK 多层，在每个边界打日志看数据怎么流过去，跑一次拿到证据看**哪一层断了**，再聚焦那一层
5. **追溯数据流**——错误在调用栈深处时，一层层往上追到坏值的源头，在源头修不在症状处修

### Phase 2：模式分析

- **找已经能跑的例子**——同 codebase 里有类似的工作代码吗？
- **对照参考实现**——按某模式实现就完整读参考代码，不要扫一眼
- **列出差异**——坏的 vs 能跑的，每一点差异都列出，不要假设"这个差异不重要"

### Phase 3：假设与验证

- **提单一假设**——写下来："我认为根因是 X，因为 Y"，要具体
- **最小测试**——最小改动验证假设，一次只变一个变量
- **验证再继续**——失败就提新假设，**不要在上面加更多 fix**
- **不懂就承认**——说"我不理解 X"，不要装懂

### Phase 4：实施

1. **复现路径**——用最简方式能复现 bug（不写单测，但要有"做完哪个操作能看出 bug 没了"的明确路径）
2. **单点修复**——只修根因，不要"顺手"重构，一次一个改动
3. **验证修好**——复现路径走一遍，确认 bug 消失；可以用 `/verify` skill 跑完整验证
4. **修不好怎么办**：
   - < 3 次：回 Phase 1，带上新信息重新分析
   - **≥ 3 次：停止 fix，质疑架构**（见下）
5. **3+ 次 fix 失败 = 架构问题**——每个 fix 都揭示新的耦合 / 都需要"大规模重构" / 都在别处制造新症状 → 这不是假设错了，是架构不对，**停下找用户讨论**

## 红线 - 看到自己这么想就停

- "先快速修一下，回头再调查"
- "试试改 X 看看行不行"
- "可能是 X，先修 X"
- "我没完全懂但这样改可能行"
- "再试一次就好"（已 2+ 次）
- 每个 fix 都在别处暴露新问题

**全部都意味着：停。回 Phase 1。**

## 常见自我合理化

| 借口 | 真相 |
|---|---|
| "问题简单不用走流程" | 简单 bug 也有根因，流程对简单 bug 也快 |
| "紧急没时间走流程" | 系统化比瞎试快得多 |
| "先随便试一下，不行再调查" | 第一次试就定基调，一开始就走对 |
| "我看到问题了，直接修" | 看到症状 ≠ 理解根因 |
| "多个改动一起改省事" | 不能隔离哪个起作用，制造新 bug |
| "再试一次"（已 2+ 次失败） | 3+ 次失败 = 架构问题，质疑模式而非继续 fix |

## 用户的信号说明你走错了

- "是这样吗？" — 你假设了没验证
- "能不能让我们看到 ...?" — 你应该先加证据收集
- "别猜了" — 你在没理解时提 fix
- "深度思考一下" — 质疑根本，不只是症状
- "卡住了？" — 你的方法不对

**看到这些：停。回 Phase 1。**

## "真的没有根因" 怎么办

走完流程后确认是环境/时序/外部因素：
1. 流程已完成，记下调查过程
2. 实施适当处理（重试、超时、错误提示）
3. 加监控/日志方便未来再现

**但**：95% 的"没有根因"其实是调查不彻底。

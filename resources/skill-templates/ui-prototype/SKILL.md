# UI 交互原型工作流

把抽象的 UI 讨论变成能点、能切、能盯着看的对比原型；demo 是跟随产品演进的活文档，不是一次性用品。

## 流程

1. **提取待拍板决策点**：当前讨论中所有未收敛的结构决策（如「融合条 vs 独立条」）逐条列出
2. **变体矩阵覆盖决策点**：每个待拍板决策各做一版变体（不是只做一版成品），加一版「现状基线」作对比；平台（macOS 红绿灯/Windows WCO）与深浅主题做成切换开关
3. **派子会话或自做单文件原型**，硬规范见下
4. **验收两段**：机械验收（文件存在、关键特征 grep 抽查、零外链）+ 用户观感验收（不可代替）
5. 观感反馈迭代 demo；拍板后：落选变体删除、采纳变体改标「现状」（或删旧现状）、更新设计文档

## 硬规范（单文件原型）

- 单文件 HTML，样式内嵌 `<style>`，图标内联 SVG，**零 CDN/外链**（离线可用）
- 配色取应用真实主题色（浅 #F5F1E8/文字 #33302B，深 #1E242C/文字 #C6CBD2），严禁默认蓝紫；accent 绿 #10B981/红 #EF4444
- 假数据要真实感：真实感标题、运行中/未读/子会话等状态齐全，不用 lorem
- 关键状态可交互：不只是能看，模式切换/列表收起/tab 联动要能点出来
- demo 控制条（形态/平台/主题开关）视觉上明显不属于原型，**默认收起**（右下角折叠按钮），不遮挡原型任何区域
- 交付位置 `dogear/design/<topic>-demo.html`

## 活文档纪律（lazy sync）

- **平时不同步**，但**每次取用时第一步强制对齐现状基线**：对照当前布局代码更新「现状」变体，再叠加新讨论的变体——严禁在过期基线上讨论
- **变体生命周期**：方案落地 → 对应变体改标「现状」并删除旧现状；被否变体直接删（git 历史留存）
- **只对齐到结构级**（布局/层级/关键状态），不追像素与完整交互逻辑——否则变成维护第二份 UI，必然腐烂
- 对齐过程本身就是 UI 审计：发现产品 UI 悄悄漂移的不一致是额外收益

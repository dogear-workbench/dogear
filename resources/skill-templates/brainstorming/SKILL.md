# Brainstorming

把想法通过自然对话变成可实施的设计文档。规划在前，动手在后。

## 强制纪律

绕过本 skill 直接给方案是错误行为——跳过讨论 = 用 50% 的把握去改代码。

## 流程

### Step 1：盘点现状（硬闸门）

讨论任何「新做 X」之前，先查代码库是否已有相似机制（Grep / Glob / codebase-map），列出清单逐项说明复用 / 不复用理由。没有查证过的东西不得以「新做」提给用户——把已有功能当新功能提议，是本项目已发生过的真实失败。同时用 dogear__RecallMemory 查有无相关记忆（坑 / 决策 / 用户偏好），命中即吸收进方案。

### Step 2：一次只问一个问题

焦点：目的、约束、成功标准。

### Step 3：探索方案

- 提 2-3 种思路，附权衡（性能 / 可维护性 / 实施成本）
- 先说推荐项 + 理由，再列其他
- 不假装中立，有偏好就讲

### Step 4：分段呈现设计

分段验证，别一次甩完整设计；覆盖架构 / 模块边界 / 数据流 / 错误处理。

## 设计文档落盘

讨论清楚后，写到 `dogear/plans/YYYY-MM/YYYY-MM-DD/<topic>-design.md`：

```markdown
# <Topic> 设计

**背景**：（为什么要做）
**目标**：（要达成什么）
**架构**：（核心做法 + 排除的选项及原因）
**模块边界**：（涉及哪些文件 / store / service / IPC 路由）
**数据流**：（从 X 到 Y 怎么走）
**错误处理 / 边界情况**：（已识别的）
**未决问题**：（讨论时没拍板的，留给实施时补）
```

## 后续衔接

设计文档落盘后、挂任务或执行前，必须显式过一遍「是否分步骤」判断：
- 满足分步条件（标准见系统「笔记存卡纪律」段：跨 ≥3 文件且有依赖 / 需跨会话续做 / 架构层变更）时 → 用 staged-impl skill 写实施计划，CreateTask 的 planPath 指向 plan.md
- 都不满足 → 明说不分步骤的理由——「不分」也是决策，不能默默跳过

判断完再确认执行时机：挂计划栏（dogear__CreateTask）还是立即执行。

## 关键原则

- YAGNI，砍掉没必要的特性
- 先推荐再列选项，不假装中立
- 拿不准就回头，不要硬撑

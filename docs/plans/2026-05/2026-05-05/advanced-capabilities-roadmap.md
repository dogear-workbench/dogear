# Dogear 进阶能力路线图

> 创建日期：2026-05-05
> 状态：规划中（未启动）
> 定位：从"AI 驱动的阅读器"升级为"有记忆、能后台工作、能理解代码项目的个人 agent 平台"

---

## 背景与动机

基础功能已稳定：书籍阅读、股票分析、文章解析、AI Agent 问答都可正常使用。
下一阶段要突破的是 **agent 能力层**：让 agent 有持久记忆、能后台自主工作、能跨越单次会话的边界。

## 核心设计原则（从 pi-mono 哲学借鉴）

1. **Observability first**：每个 token、每次状态变化用户都应看得见
2. **Lazy loading for long-tail**：高频恒常的东西自动注入；低频情境的东西按需查询
3. **Core 纯粹 + 扩展随便加**：核心系统小而稳定，能力扩展走独立机制
4. **不过度重构**：保留 Claude Agent SDK 作为对话底座，不切换框架

## 能力清单（按优先级排序）

### 🎯 里程碑 1：规则文件化 + 静态记忆系统（已完成）

**状态**：2026-05-06 联调完成

**目标**：建立"规则层 + 记忆层"的双轨架构，为后续所有能力打地基。

**核心变更**：
- 规则层三级（用户级 / 工作区级 / 临时）全部走 CLAUDE.md 文件机制，SDK 自动加载
- 记忆系统作为**独立于规则层的第五条线**，分两层存储
  - **核心档案**（core-profile.md）：自动注入，硬限 ~500 token，存"用户是谁"
  - **主题记忆**（topics/*.md）：按需查询，agent 通过 `RecallMemory` 工具访问
- 设置页新增记忆管理 Tab，支持查看/编辑/删除记忆

**里程碑 1 不做的事**：
- ❌ 自动从会话提炼记忆（留到里程碑 2）
- ❌ 后台定时任务（留到里程碑 2）
- ❌ 多供应商模型抽象（现有代理 API 已够用）

**详细设计见**：`milestone-1-memory-foundation.md`

**2026-05-07 追加决策**：
- core-profile 的**定位调整**：里程碑 1 只做数据结构 + IPC + UI 壳子，**不要求用户手动填写**。做梦系统（里程碑 2）才是 core-profile 的真正生产者，用户的角色是"巡检员"而非"作者"。
- 里程碑 1 的**实际主交付是 topics + RecallMemory**——用户可以让 agent 主动保存主题记忆，agent 可以按关键词查询。

### 🛠️ 里程碑 1.5：工作区交互重构 + Skill 瘦身（本轮新增）

**状态**：设计中（2026-05-07 规划）

**目标**：把 dogear 从"为少量调试设计的应用"升级为"可以长期日用的个人 agent 平台"。

**背景**：随着用户开始把 dogear 作为日常开发工具使用（"在 dogear 里聊 dogear 开发"），暴露出两个核心痛点：

1. **交互层面**：工作区切换会销毁所有会话（`clearWorkspace` 主动关闭 session），用户无法跨工作区并行工作
2. **上下文成本层面**：全局 CLAUDE.md、项目 CLAUDE.md、18 个 MCP 工具全量注入每个会话，导致注意力分散、token 浪费

**核心变更**：

- **A. 工作区交互模型重构**：
  - 从"工作区为主体"→"会话为主体"，工作区退化为会话的属性
  - 打开的会话在顶部 Tab 栏，点击即切换聚焦；聚焦会话的工作区决定左右栏内容
  - 后端 session 不再随工作区切换关闭，Tab 关闭才释放连接
  - 活跃会话上限 10 个，超出提示用户
  - 工作区切换用 Command 浮窗，高频切换低摩擦
  - 工作区级 CLAUDE.md 编辑入口外移到顶部"工作区规则"按钮

- **B. 规则和工具瘦身**：
  - `~/.claude/CLAUDE.md` 只留通用协作偏好（中文、先规划后实现、开发阶段不做兼容）
  - 项目 `.claude/CLAUDE.md` 砍掉"核心文件功能索引"等给人看的文档部分，agent 需要时用 Glob/Grep 自己探索
  - 低频重计算工具（股票分析/书籍分析/文章解析）转为 Skill + 脚本模式，通过 SKILL.md description 按需激活
  - 高频基础工具（RecallMemory / 股票基础行情 / 文章列表 等）保留 MCP 形式
  - 用户在工作区配置启用的 Skill，其声明的工具自动进 `allowedTools` 白名单（不再权限询问）

- **C. 单实例锁修复**：
  - dev 和 prod 用不同 `appUserModelId`，允许同时运行

**详细设计见**：`milestone-1.5-workspace-ux-and-skill.md`

**1.5 不做的事**：
- ❌ 左侧对话列表的"最近优先 + 老对话折叠"排序（记录到后续独立优化）
- ❌ 跨工作区的会话或记忆关联（后续里程碑讨论）
- ❌ 独立会话窗口内部的 Tab 化（保持单会话锁定）

### 🌙 里程碑 2：做梦系统（会话提炼）→ 已升级为"记忆参谋"

> **2026-06-02 升级**：本里程碑已从"被动做梦系统"扩展为"记忆参谋"（三级流水线：脚本去噪 → 单会话提炼 → 跨会话综合，外加首页仪表盘）。
> **详细大计划见**：`../../2026-06/2026-06-02/milestone-2-memory-copilot.md`（含 8 条关键决策 + Phase A/B/C/D 阶段划分）。下方为最初设想，保留作历史参考。

**目标**：让 agent 在后台自动从历史会话中提炼记忆，不打扰用户。

**核心功能**：
- **触发时机**：会话关闭时触发（一次一次来，先不上定时批处理）
- **处理内容**：读 JSONL 会话历史 → 提炼 "新增/更新" 的核心档案条目 + 主题记忆
- **模型选择**：用便宜模型（Haiku 4.5 或走代理用 Gemini Flash），通过现有 Claude 格式 API
- **写入策略**：全自动写入，用户在设置页"最近记忆"巡检，坏记忆就地编辑/删除
- **资源感知（简化版）**：只在"主对话空闲"时启动做梦任务，避免抢占
  - 不做挂起/恢复（复杂度太高）
  - 每个任务硬超时 30 秒，不完成就放弃

**依赖**：里程碑 1 完成

**预期产出**：
- 新增 `electron/main/services/memory/dream-service.ts`
- 复用 `agent-manager.ts` Worker 池跑做梦任务
- 设置页记忆 Tab 增加"最近生成"分组 + 确认/编辑 UI

### 🧠 里程碑 3：记忆反馈闭环

**目标**：识别 agent "该 recall 却没 recall" 的情况，反过来强化规则。

**核心功能**：
- 做梦系统加工会话时，检测"agent 在 X 场景下本该查 Y 记忆但没查"的 pattern
- 自动往 CLAUDE.md 追加提示条目（待用户确认）
- 记忆工具返回 actionable 提示，而非仅返回内容

**依赖**：里程碑 2 完成且记忆量积累到一定规模

---

### 🏗️ 里程碑 4：代码项目整体理解

**目标**：让 agent 能读懂 dogear 自身（或其他任何代码项目）的架构和历史，在"修改代码"场景下与用户在同一信息层。

**核心设计**（不换框架，用现有 SDK + 更好的项目索引）：
- 新增 `project-index` skill：扫代码 → 建 symbol/依赖图 → 作为工具供 agent 查询
- 索引结构：符号定义位置 + 依赖关系 + 模块职责（从 CLAUDE.md / 注释中提取）
- 增量更新：监听文件变更，只重扫改动的文件
- 与 pi 的差异：pi 是"让模型靠 bash 自己探索"，dogear 是"给模型一张地图"——前者适合命令行 CLI，后者适合有 UI 的桌面应用

**依赖**：前三个里程碑的经验积累（记忆系统已稳定运行）

---

### 🤝 里程碑 5：Sub-Agent 委派（2026-05-07 新增）

**目标**：让主 agent 能把专项任务委派给预定义的 sub-agent，消除单会话上下文污染。

**背景**：里程碑 1.5 已经用 Skill 降低了工具 schema 成本，但对于"股票深度研究"、"多角度审查"这类任务，最好的隔离方式是让一个独立 agent 带着专属工具集和记忆独立运行，结果回传给主对话。

**核心功能**：
- 预定义几个 sub-agent：`stock-analyst` / `book-analyst` / `researcher`
- 每个 sub-agent = 独立系统提示 + 工具白名单 + Skill 白名单 + 模型选择
- 主 agent 通过 SDK 的 `Task` 工具委派任务，sub-agent 独立上下文执行
- UI 在主会话显示"委派中（任务 ID: xxx）"，完成后插入结果卡片

**依赖**：里程碑 1.5 的 Skill 系统稳定运行

---

### 👥 里程碑 6：Agent Teams 探索（实验性，谨慎）

**目标**：多个独立 agent 并行协作，通过共享任务列表和 mailbox 直接通信。

**和 Sub-Agent 的区别**：
- Sub-Agent 是主从结构（主委派、子执行、子返回结果）
- Agent Teams 是对等结构（成员直接互相发消息、共享任务列表、自我协调）
- 适合"研究和审查"、"竞争假设调试"这类需要讨论的任务

**前置**：
- SDK 需要 Claude Code v2.1.32+，`CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`
- dogear 需要自己实现 Team UI（多面板/会话切换），因为 SDK 的 Team 默认用 tmux 或 iTerm2 的 CLI 交互
- 只支持 Claude 家族模型（SendMessage、任务管理等协调工具是 Claude Code 特有）

**为什么排后**：
- 实验性 feature，API 可能变
- UI 工程量大
- Sub-Agent 能覆盖 80% 的委派需求

**目标**：让 agent 能读懂 dogear 自身（或其他任何代码项目）的架构和历史。

**核心设计**：

- 与 pi 的差异：pi 是"让模型靠 bash 自己探索"，dogear 是"给模型一张地图"

### 🔧 里程碑 8：自定义工具完全 lazy loading（谨慎，可能不做）

**目标**：长尾的自定义工具从 system prompt 里完全移出，agent 按需发现。

**前置条件**：
- 里程碑 1.5 的 Skill 系统已经消化了大部分工具 schema 的成本
- 如果 Skill + Sub-Agent 的组合已经能让 system prompt 足够精简，这个里程碑可能**不再必要**

**实施方式**（如果做）：
- 高频工具继续 eager 注册
- 长尾工具注册进工具注册表但**不注入 system prompt**
- 提供 `DiscoverTools(category)` 让 agent 按类别查询可用工具

**为什么可能不做**：里程碑 1.5 的 Skill 瘦身如果效果足够好，这层就是过度工程。

## 跨里程碑的共同约束

### 不做什么
- 不切换 agent 框架（继续用 Claude Agent SDK）
- 不引入 pi-ai（现有代理 API 已经提供多供应商的 Claude 格式访问）
- 不做向量库/embedding 检索（关键词 + 时间窗口够用）
- 不做挂起式做梦（调度太复杂，用"空闲触发 + 硬超时"代替）

### 必做什么
- 每个里程碑结束都要产出可独立使用的功能，不堆在最后合并
- 每个里程碑都有对应的设计文档（本路线图 + 单独的 `milestone-N-*.md`）
- 单用户自用的定位——不搞权限/审核/confidence score 这类防御性设计，信任用户自己 review

## 开放问题（后续讨论）

1. **跨工作区的记忆如何关联**：同一个人在 dogear 工作区讨论的"设计哲学"可能和 books 工作区讨论的"某本哲学书"有关联。要不要做跨工作区的弱链接？（先不做，记录）
2. **记忆的时间衰减**：半年前的偏好现在还算数吗？要不要给记忆打时间戳，做"半衰期"机制？（里程碑 3 再看）
3. **做梦系统的失败处理**：如果做梦模型挂了，怎么保证不影响主对话？（里程碑 2 解决）

## 已记录的设计决策

### 关于 tempPrompt 的语义（2026-05-06 讨论）

**背景**：`conversation.tempPrompt` 字段 UI 上叫"临时提示词"，但实际是**对话私有持久**字段（存在 `conversations.json`，跟随对话归档/重开都在）。讨论中发现 UI 文案与实际语义不匹配。

**决策**：保持数据结构和行为不变，**只改 UI 文案**为"对话规则"，明确说明"会跟随对话保存"。

**原因**：
1. 持久化行为反而**符合"归档的对话作为记忆提炼原材料"的定位**——tempPrompt 应该跟归档一起进冷库
2. "真·临时"（只影响下一轮）的需求有替代方案：用户直接在消息里写"用英文回答：xxx"即可
3. 现有代码里多处使用 `tempPrompt` 变量名，大改会伤及无辜

**后续可能**：如果将来真需要"下一轮临时指令"，再新增 `nextTurnHint` 字段（不存盘、发送后清空），两个字段并存。

### 关于 `systemPromptAppend` 字段（2026-05-06 讨论）

**背景**：早期全局追加 prompt 字段，后被 persona + tempPrompt 替代，标记为 `@deprecated` 但代码里还在拼接。`.dogear/settings.json` 里一条测试用的旧值一直被注入所有对话。

**决策**：**里程碑 1 的 Step 0 清理**。移除字段定义、移除拼接逻辑、手动清理用户数据文件。

**原因**：
- 项目 CLAUDE.md 明确"开发阶段不做兼容"
- 不清理的话，新增 core-profile 注入会让 buildSystemPrompt 拼接 6 个来源，心智负担过大

### 关于 Agent Teams 的兼容性（2026-05-07 讨论）

**背景**：SDK 0.2.119 已包含 Team 原语（`teammateMode`、`TeammateIdle` hook、`SendMessage` 工具、任务管理）。但 Team 的默认交互依赖 tmux / iTerm2 的多面板，这些 CLI UX 在 dogear 桌面应用里不可复用。

**决策**：Team 挪到里程碑 6（实验性、谨慎）；先在里程碑 5 做 Sub-Agent（SDK 原生稳定支持）。

**原因**：
1. Sub-Agent 能覆盖"带专业工具箱的一次性委派"这个 80% 场景
2. Team 需要自己实现多面板 UI，工程量大
3. Team 只支持 Claude 家族模型（依赖 SendMessage 等 Claude Code 特有工具），和 dogear"走代理 API 多模型"的定位冲突

### 关于工作区交互模型的转变（2026-05-07 讨论）

**背景**：里程碑 1 联调完成后，用户开始把 dogear 用作日常开发工具（"在 dogear 里聊 dogear 开发"），立刻暴露了几个问题：
- 开发环境和生产环境的 Electron 单实例锁冲突，无法同时运行
- 切换工作区会关闭所有活跃会话（`clearWorkspace` 里调用 `closeQueryBasedSession`），破坏跨工作区并行工作的可能性

**决策**：新增里程碑 1.5，把工作区交互模型从"工作区为主体"重构为"会话为主体"：
- Tab 栏承载活跃会话（建立了 Query 连接的会话），点击即切换聚焦
- 聚焦会话的工作区决定左右栏内容（对话列表、文件树）
- 工作区切换用 Command 浮窗，不再销毁会话
- 上限 10 个活跃连接

**原因**：
1. 让用户能在"改代码的会话"和"看股票的会话"之间自由切换，互不干扰
2. 保留长时间跑的 agent 任务（文章解析、股票分析），切换工作区不会中断
3. 符合浏览器 Tab 模型的用户直觉

**详细设计见**：`milestone-1.5-workspace-ux-and-skill.md`

### 关于 Skill 承载工具的路径选择（2026-05-07 讨论）

**背景**：讨论三条路径（A 仅激活提示 / B 动态加载工具 / C 混合）。

**决策**：走 **C3 混合路径**：
- 高频基础工具（< 8 个）保留 MCP 形式，始终注册
- 低频重计算工具（股票分析 6 个、书籍分析 3 个、文章解析 2 个）转为 Skill + 可执行脚本
- Skill 的 description 进 system prompt（便宜），详细 SKILL.md 和工具激活按需发生
- 用户在工作区启用的 Skill，其声明的工具（如 `Bash(python scripts/*.py)`）自动进 `allowedTools`，不触发权限询问

**原因**：
1. 路径 A 只是"改皮",工具 schema 还在 system prompt 里,没实际收益
2. 路径 B 需要 SDK 运行时动态注册工具，SDK 原生不支持
3. 路径 C 利用 SDK 已有的 Skill 机制，天然契合"股票分析 = Python 脚本"这类既有架构

### 关于 core-profile 的定位调整（2026-05-07 讨论）

**背景**：里程碑 1 实现的 core-profile.md 最初设计让用户手动维护，但用户反馈"这本来就是为做梦系统自动生成设计的壳子"。

**决策**：
- 里程碑 1 的 core-profile 数据结构 + IPC + UI **保留**，但不要求用户手动填写
- 做梦系统（里程碑 2）才是 core-profile 的真正生产者
- 里程碑 1 的主交付是 topics + RecallMemory
- 设置页 MemoryTab 的 core-profile 标签在空态下显示"等待做梦系统自动生成"

**原因**：手动维护核心档案和 CLAUDE.md 功能重叠，让用户重复维护两份相似内容是反设计的。

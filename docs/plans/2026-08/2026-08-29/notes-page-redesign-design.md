# 笔记页重做与任务系统 设计

**日期**：2026-08-29
**来源**：笔记 16b1h86d（编辑体验诊断）的延续讨论。前置文档：`note-agent-collaboration-design.md`（同日，人机协作闭环——本文的引用按钮、来源行以其为依赖）。

## 背景

- 现状结构性错位：MDXEditor 塞在 288px 详情栏（`activeNoteId ? 'w-72'`），元数据常驻挤压正文，无独立标题，工具栏「文档感」——写想法的动作展不开，用户确认非适应问题
- 待办错位：`Note.todos` 挤在编辑区，但多数笔记没有待办；用户实际工作流是「会话里聊透 → 新建会话让 agent 实施 → 看结果」，全程手动
- 用户口味拍板：Bear 模型——干净、功能少、正文是主体、基础编辑顺手；不要 Craft/Heptabase 的重结构

## 目标

1. 笔记页重做为「列表 | 完整编辑区」骨架，编辑区 Bear 化
2. 待办从笔记编辑区移除：人的待办 = 正文 `- [ ]` 文字
3. 任务系统：独立 Task 对象，挂载即排队，自动创建执行会话实施，主进程通知，审核过/打回
4. 任务视图与笔记视图同页切换，共用骨架

**明确不做**：笔记侧「转任务」入口（任务产生唯一路径 = 会话侧挂载）、列表拖宽、沉浸模式完整版（一期=隐藏列表）、编辑器更换（Tiptap Spike 另期）、双链、正文内标签语法。

## 架构

### 1. 笔记页骨架

```
顶栏：[笔记] [任务] 切换 + 搜索 + ＋新建
左：列表区（300px 固定）
右：详情区（笔记编辑区 / 任务详情，两视图共用）
```

### 2. 笔记编辑区（Bear 化）

```
标题（独立输入，大字号，新建即聚焦）
8/29 · 🔗 · #3 · 💬      ← meta 行：小灰字+图标+tooltip
   🔗 来源会话（Agent 存的卡才有）→ 点击跳回讨论
   #3 标签数 → 点击展开标签芯片与引用列表（行内展开/收起）
   💬 引用按钮（链路1入口，列表卡片 hover 处同款）
正文（max-width 760px 居中）
工具栏：编辑区聚焦时顶部浮现轻量一条，失焦消失
```

行为规则：
- 待办不渲染在编辑区（人的待办 = 正文文字）
- 保存状态在 meta 行角落短暂闪现；**修复**保存失败仍显示「已保存」的问题（16b1h86d 前置诊断 s3pg7hi0 提及）
- 键盘流：Esc 返回列表、Ctrl+Enter 保存返回、自动保存
- 沉浸模式一期形态：双击分隔条/快捷键隐藏列表
- 工具栏一期为顶部浮现条；换 Tiptap 后升级为选中文字浮动气泡

### 3. 任务系统

**对象模型**：

```ts
Task {
  id: string
  title: string
  status: 'queued' | 'running' | 'review' | 'done' | 'rejected'
  planPath: string           // docs/plans/... 文件引用（不复制内容）
  originSessionId?: string   // 产生任务的会话（与卡片来源身份证同构）
  execSessionId?: string     // 执行会话
  result?: string            // 结果摘要（执行完成时写回）
  createdAt / updatedAt
}
```

**生命周期**：

```
queued（挂载）
  → running（队列取出，自动创建执行会话，启动上下文=任务定义+plan路径）
  → review（执行会话结束，结果写回，主进程系统通知）
  → done（用户点「通过」）
  → rejected（用户点「打回」；重新执行=用户改后手动重挂）
```

**关键决策**：
- 队列串行执行，一次一个（成本与并发约束，任务多再放开）
- 执行会话 = 普通会话（自动创建），内部是否派子会话由其自行决定——对齐用户现有「新建会话去实施」的心智，过程即会话消息流，天然可回看可介入
- 结果不进任何主会话；主进程系统通知（Electron Notification）+ 应用内待审徽章
- plan 保持文件存储，任务持有路径引用，详情页聚合渲染（计划+执行会话+结果一站式是视图聚合，非存储聚合）
- 任务产生唯一入口：会话侧挂载（存 plan 后「存为任务」，路径自动；存量 plan 文件树右键「挂为任务」）

### 4. 任务视图

```
左：任务列表按状态分组（排队/执行中/待审/已完成）
右：任务详情 = 标题+状态徽章 / plan 文件内容渲染 / 执行会话链接 / 结果摘要 / [通过][打回]
通知点击深链到待审任务详情
```

## 数据流

**挂载**：会话聊透 → plan 落盘 → Agent 调 `dogear__CreateTask(planPath, title, originSessionId)` → status=queued → 列表可见
**执行**：队列执行器取出 queued → 创建执行会话（启动 prompt=任务定义+plan 路径）→ running → 会话结束 → result 写回 → review + 系统通知
**审核**：任务详情 [通过]→done / [打回]→rejected（tipc）→ 打回后用户修改 plan 手动重挂

## 错误处理 / 边界情况

- 执行会话失败/卡死：Task 进 rejected 或标记执行失败态，通知用户
- 应用退出时队列中断：重启后 queued 任务可恢复执行（running 态置回 queued）
- plan 文件被移动/删除：任务详情渲染失败提示，任务仍可取消
- 通知点击时任务已被处理：深链到详情当前态，不报错

## 未决问题

1. `Note.todos` frontmatter 的迁移策略：现有 staged-execution 纪律、`ListTodos`、卡片待办体系建立在 Note.todos 上——任务系统上线后的兼容期（双轨/一次性迁移/仅新任务走 Task）实施时定
2. 执行会话「结束」的判定信号（交付即结束 vs 显式标记），与执行会话提示词的约定
3. 打回后的反馈通道（纯终结+重挂 vs 打回时可附一句反馈）——一期先做终结+重挂
4. 保存失败仍显示「已保存」的根因修复方式（实施时查现有保存链路）
5. meta 行图标的最终形态（哪些信息值得占位：日期/来源/标签数/引用/保存状态）

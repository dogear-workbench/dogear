# 智能分类补漏（categorize-sweep）设计

**背景**：scheduler 的 categorize builtin 被映射到 triggerFullRebuild，导致「组卡提炼→智能分类」任务链每次触发全量重扫（8-19 以来自动跑了 8 次，每次对 3 个工作区循环、61 张组卡重决策 10-30 分钟），违反 2026-06-10 设计原则「避免雪崩：每次新摘要卡只触发局部决策，不全量回扫」。用户已手动禁用该任务，但代码映射仍在。

**目标**：让「组卡提炼 → 智能分组 → 复盘报告」三段流程做到：可控（各段可单独触发/禁用）+ 断点续跑（中途断了从断点收敛，不重头）。

**架构**：承认两层分工——scheduler 管「时序」（何时开始一轮），事件链管「数据流」（组卡 saved 瞬间带参数串增量决策，已有 chainCategorize）。断点续跑不用断点状态机，用**幂等差集**：每段从「实际状态 vs 应然状态」的差值自动恢复。

- 组卡提炼：脏组判定天然幂等（已有）
- 智能分组：差集 = 有 tags 的活跃组卡 − 已挂载分类的组；补漏任务处理差集，差集为空即 no-op（**本次新增**）
- 复盘：过时判定幂等（已有）

**排除的选项**：
- 给 scheduler 加参数化数据流（on_plan_done 带 payload）——重造 chainCategorize 已有的轮子，复杂度不划算
- 三段合并成一个「记忆维护」大任务——黑盒化，无法单独控制/恢复，更糟

**模块边界与数据流**：

```
scheduler（时序层）
  组卡提炼 ──链──> 复盘                    （不变）
     └──────链──> 智能分类 = 补漏          （重定义：原 full-rebuild）
  分类整理 organize                         （不变）

事件链（数据流层，不动）
  组卡 saved ──带参数──> 增量决策           （group-digest-trigger.ts:243）

兜底（手动）
  「全量重置分类」                           （原 full-rebuild，仅设置页按钮，改名）
```

**错误处理**：sweep 查 `smartCategory.enabled === false` 直接空转返回（对齐 group-digest-trigger.ts:260 模式）；组卡读取失败跳过 + warn；无 tags 跳过并计数（summary 提示需重提炼）；归档组跳过；差集大照跑（幂等无风险）。

**未决问题**：无（已全部拍板）。
